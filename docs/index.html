Migration plan (summary)

  • Stage 0: pin the stack; re-run this suite against the production server; confirm middlebox tolerance for a 1378-byte ClientHello.
  • Stage 1 (canary): offer X25519MLKEM768 first, X25519 second; hybrid when both ends support it, classical fallback otherwise. Budget ~+15–20% handshake CPU.
  • Stage 2 (broad rollout): extend the hybrid preference to all traffic once the canary meets the rollback criteria; keep X25519 offered as the fallback.
  • Stage 3 (hybrid-only, optional, later): only after every supported client negotiates the hybrid.
  • Rollback (config change only) if: hybrid failure rate > 1% over 5 min; median latency > 10 ms above baseline over 15 min; server CPU per handshake > 1 ms above baseline; any confirmed ClientHello-size failure; any stall-related unavailability.
  • Slow-loris mitigations: handshake timeout, per-IP limits on half-open handshakes, a concurrent server.

Full plan: docs/migration-plan.md. Methodology and limitations: docs/methodology.md. Claims-to-evidence index: docs/evidence-index.md.

Reproduction

bash scripts/clean_reproduce.sh rebuilds the pinned stack from fixtures/, regenerates certificates, re-runs the full suite, and compares re-derived headline numbers against the shipped ones (outputs/fresh-clone-compare.txt). bash scripts/verify_digests.sh checks every shipped file against SHA256SUMS. All tests run against a local openssl s_server on 127.0.0.1 only.

Pinned environment: OpenSSL 3.0.13, liboqs 0.16.0, oqs-provider 0.12.0. Logs: outputs/ (run1 + run2, unedited). Limitations L1–L8 in docs/methodology.md apply — notably, the test server is single-threaded and the certificate is classical ECDSA P-384.
